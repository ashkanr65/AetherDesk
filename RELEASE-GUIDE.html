AETHERDESK • WINDOWS RELEASE OPERATIONS

AetherDesk build and release guide

Prepare, sign, upload, publish and test an AetherDesk update yourself, using the existing Rust build kit and protected signing key.

Prepared 19 October 2026. Local paths match this PC. The next-release example is 0.1.2 build 3; build 2 is already published. Change the example for each future release.

Publishing a normal release enables updates for all eligible users. Drafts and previews do not appear in the application's stable update channel. Increasing a version in a text file is not enough: the new executable must be built, packaged and signed.

This does not transfer the signing key. A different PC or Windows account still needs authorized access to the existing protected key. You can also use the public project's manual signing workflow; its configured Actions secret is separate from this local Python environment.

The project repository also has the encrypted UPDATE_SIGNING_KEY Actions secret. Do not run key initialization as a routine release step, change the pinned public key, export secrets into the source tree, or upload keys. Replacing the key prevents existing clients from trusting updates. Arrange an approved key backup before replacing this PC.

2 Prepare the next version

Finish and commit feature changes first. Pull the current main only when your working tree is clean. All source changes and pushes stay on main.

PowerShell • synchronize clean source
Set-Location -LiteralPath $Source
if ((git branch --show-current) -ne 'main') { throw 'Switch to main first' }
if (@(git status --porcelain).Count) { throw 'Review and commit current changes first' }
git pull --ff-only origin main
if ($LASTEXITCODE -ne 0) { throw 'Source synchronization failed' }

Use a unique version/build pair for every publication. Keep the version for a small rebuild and increase the build number. For a feature release, choose a new numeric version and a positive build number. Numeric versions such as 0.1.3 are supported; the previous 0.0.1.AI-R naming idea is not the current version format. Never reuse a published pair or relabel an old executable.

PowerShell • example next release, edit these two values
$ReleaseVersion = '0.1.2'
$ReleaseBuild = 3
@{ version = $ReleaseVersion; build = $ReleaseBuild } |
    ConvertTo-Json | Set-Content -LiteralPath (Join-Path $Source 'release.json') -Encoding UTF8
& (Join-Path $Source 'tools\build-kit\Release-Version.ps1') -Repository $Source
notepad.exe (Join-Path $Source 'RELEASE-NOTES.md')

Edit and save the notes in Notepad, then close it. Describe the changes and known limitations. Do not copy old test results as proof that the new build passed. The kit synchronizes native package versions in its snapshot; do not edit Cargo lockfiles by hand for this routine step.

PowerShell • review, commit and push before building
git diff -- release.json RELEASE-NOTES.md
git -c core.autocrlf=false add -- release.json RELEASE-NOTES.md
if ($LASTEXITCODE -ne 0) { throw 'Staging failed' }
git -c core.autocrlf=false commit -m "Prepare AetherDesk $ReleaseVersion build $ReleaseBuild"
if ($LASTEXITCODE -ne 0) { throw 'Commit failed' }
git push origin main
if ($LASTEXITCODE -ne 0) { throw 'Main push failed' }
if (@(git status --porcelain).Count) { throw 'Working tree is not clean' }

3 Build the application

Before starting, preserve an older working installation outside the output folder. Keep its installer or portable package for recovery and upgrade testing. The full-build launchers remove old packages, logs and reports. Do not run the older copy from a folder that the kit cleans.

In the build kit folder, double-click one launcher:

LauncherUse
Build-Everything.cmdInstaller and portable ZIP; frees build caches after success.
Build-Faster.cmdInstaller and portable ZIP; keeps caches for faster later builds, using more disk space.
Build-Portable-Only.cmd or Build-Portable-Faster.cmdPortable only. The main release procedure below expects both distributions; use a full build when publishing both.

Wait for every required stage to pass. If a stage fails, stop and inspect the newest log; do not upload an older output by mistake. Timings are saved in reports\build-timing.json. Do not change runtime source during release preparation: snapshot builds exclude later checkout changes.

4 Check the completed build

If you opened a new PowerShell window, repeat section 1 to restore the path variables. The following checks read files and validate packaging; they do not compile the application.

PowerShell • validate the full build and package
Set-Location -LiteralPath $Source
$timing = Get-Content -LiteralPath (Join-Path $Output 'reports\build-timing.json') -Raw | ConvertFrom-Json
if ($timing.status -ne 'Passed' -or $timing.steps.Count -ne 7 -or
    @($timing.steps | Where-Object { $_.status -ne 'Passed' }).Count) {
    throw 'A complete seven-stage build has not passed'
}
$Package = (Get-Content -LiteralPath (Join-Path $Output 'LATEST-FOLDER.txt') -Raw).Trim()
$Installer = (Get-Content -LiteralPath (Join-Path $Output 'LATEST-INSTALLER.txt') -Raw).Trim()
if (!(Test-Path -LiteralPath $Installer -PathType Leaf)) { throw 'Installer is missing' }
$built = Get-Content -LiteralPath (Join-Path $Package 'release.json') -Raw | ConvertFrom-Json
$planned = Get-Content -LiteralPath (Join-Path $Source 'release.json') -Raw | ConvertFrom-Json
if ($built.version -ne $planned.version -or $built.build -ne $planned.build) {
    throw 'The package does not match the planned release'
}
. (Join-Path $Source 'tools\rust-build-kit\Build-Common.ps1')
Verify-RustPackage $Package
$info = Get-Content -LiteralPath (Join-Path $Package 'build-info.json') -Raw | ConvertFrom-Json
if ($info.fingerprint -ne (Get-SourceFingerprint)) {
    throw 'Source changed since this package was built. Review before releasing.'
}
Write-Host "Verified $($built.version) build $($built.build); build time $($timing.elapsed)"
Get-Content -LiteralPath (Join-Path $Package 'verification\windows-regressions.json') -TotalCount 14
Get-Content -LiteralPath (Join-Path $Package 'agent\linux-x86_64\regression-results.json') -TotalCount 14
Get-Content -LiteralPath (Join-Path $Package 'verification\x11-runtime.json')

Check compilerTestsPassed: true, matching catalog hashes and successful bundled X11 evidence. The reports deliberately keep live acceptance and complete replacement readiness separate. A compiler pass does not prove every live feature works.

Test the new package directly before release: launch AetherDesk.exe from its complete folder, check both themes, SSH/SFTP/X11/desktop, keyboard and mouse, editor opening/closing, AI and your changed features. Finish these tests and close the new copy; keep the old copy available for the real upgrade. Do not run just the EXE after copying it out of its runtime folder.

5 Prepare signed release files

Use the protected key already configured on this Windows account. The publisher creates a flat ZIP for the updater, copies the installer under the public filename and signs metadata containing package hashes and the complete file inventory. Use these newly prepared files, rather than uploading the kit's original outer-folder ZIP.

PowerShell • prepare and verify the signed release
$release = Get-Content -LiteralPath (Join-Path $Package 'release.json') -Raw | ConvertFrom-Json
$Tag = 'v' + $release.version + '-build' + $release.build
$Signed = Join-Path $Output ('releases\' + $release.version + '-build' + $release.build + '-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
& $PublisherPython (Join-Path $Source 'tools\rust-build-kit\update_release.py') prepare --package $Package --installer $Installer --output $Signed --notes-file (Join-Path $Source 'RELEASE-NOTES.md')
if ($LASTEXITCODE -ne 0) { throw 'Signed release preparation failed' }
& $PublisherPython (Join-Path $Source 'tools\rust-build-kit\update_release.py') verify --directory $Signed
if ($LASTEXITCODE -ne 0) { throw 'Signed release verification failed' }
Set-Content -LiteralPath (Join-Path $Output 'LATEST-SIGNED-RELEASE.txt') -Value $Signed -Encoding UTF8
Get-ChildItem -LiteralPath $Signed -File | Select-Object Name,Length
Write-Host "Release tag: $Tag"

Expected files: AetherDesk-VERSION-buildN-Setup.exe, AetherDesk-VERSION-buildN-windows-x64.zip, and update.json. Signing covers update metadata; it does not add Windows Authenticode publisher signing. Never modify a prepared ZIP, installer or metadata file. Reprepare and reverify if inputs change.

6 Verify the portable contents

This extra check reads every archive entry and compares its size and SHA-256 with the signed inventory. It does not extract a second full copy or install anything. Copy the complete box, including both PowerShell here-string markers.

PowerShell containing Python • verify every ZIP entry
@'
import base64, hashlib, json, sys, zipfile
from pathlib import Path
folder = Path(sys.argv[1])
envelope = json.loads((folder / 'update.json').read_text(encoding='utf-8-sig'))
manifest = json.loads(base64.b64decode(envelope['manifest']))
expected = {item['path']: item for item in manifest['files']}
if len(expected) != len(manifest['files']):
    raise SystemExit('Duplicate inventory entries')
with zipfile.ZipFile(folder / manifest['portable']['name']) as archive:
    entries = archive.infolist()
    if len(entries) != len(expected) or {e.filename for e in entries} != set(expected):
        raise SystemExit('ZIP inventory does not match')
    for entry in entries:
        item = expected[entry.filename]
        digest = hashlib.sha256()
        with archive.open(entry) as stream:
            for chunk in iter(lambda: stream.read(1024 * 1024), b''):
                digest.update(chunk)
        if entry.file_size != item['bytes'] or digest.hexdigest() != item['sha256']:
            raise SystemExit('Mismatch: ' + entry.filename)
print('PASS: all', len(expected), 'portable files match the signed inventory')
'@ | & $PublisherPython - $Signed
if ($LASTEXITCODE -ne 0) { throw 'Portable content verification failed' }

7 Upload a draft

The publishing script verifies signatures, asset hashes, a clean checkout and the exact source commit on public main. It creates a draft in the same AetherDesk repository and tags that source commit. It does not publish automatically.

PowerShell • create the normal-release draft
Set-Location -LiteralPath $Source
if ((git branch --show-current) -ne 'main') { throw 'Expected main' }
if (@(git status --porcelain).Count) { throw 'Review and commit outstanding source changes first' }
git push origin main
if ($LASTEXITCODE -ne 0) { throw 'Source push failed' }
& (Join-Path $Source 'tools\rust-build-kit\Publish-Update.ps1') -Directory $Signed -Python $PublisherPython

For a preview draft, add -Preview to the final command instead. Run only one variant for a release tag. Keep the draft URL printed by the script. The script throws on failure; do not ignore its error even if older terminal exit information appears successful.

If an upload fails, the draft may contain partial files. Inspect it on GitHub before retrying; the script creates a new draft rather than resuming an existing one. For an unpublished incomplete draft, remove it through GitHub and retry the same signed files. Do not remove or replace a published release to reuse its version.

8 Verify uploaded files

Run this after all uploads finish. It reads the existing Git Credential Manager sign-in without displaying the token, locates the intended release, compares all three remote digests and sizes with the local signed files, checks source privacy and records the result.

PowerShell • verify GitHub assets before publishing
$credentials = $null
$credentialLine = $null
$headers = @{}
try {
    $env:GIT_TERMINAL_PROMPT = '0'
    $env:GCM_INTERACTIVE = 'never'
    $credentials = "protocol=https`nhost=github.com`n`n" | git credential fill 2>$null
    if ($LASTEXITCODE -ne 0) { throw 'Git Credential Manager sign-in required' }
    $credentialLine = $credentials | Where-Object { $_.StartsWith('password=') } | Select-Object -First 1
    if (!$credentialLine) { throw 'GitHub credential unavailable' }
    $headers = @{ Authorization = ('Bearer ' + $credentialLine.Substring(9)); Accept = 'application/vnd.github+json'; 'X-GitHub-Api-Version' = '2022-11-28' }
    $sourceRepo = Invoke-RestMethod 'https://api.github.com/repos/ashkanr65/AetherDesk' -Headers $headers
    if ($sourceRepo.private -or $sourceRepo.default_branch -ne 'main') { throw 'Expected public AetherDesk on main' }
    $envelope = Get-Content -LiteralPath (Join-Path $Signed 'update.json') -Raw | ConvertFrom-Json
    $manifest = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($envelope.manifest)) | ConvertFrom-Json
    $Tag = 'v' + $manifest.version + '-build' + $manifest.build
    # Follow pagination so a repository with many old releases still works.
    $matches = @()
    for ($page = 1; ; $page++) {
        $batch = @(Invoke-RestMethod ("https://api.github.com/repos/ashkanr65/AetherDesk/releases?per_page=100&page=$page") -Headers $headers)
        $matches += @($batch | Where-Object { $_.tag_name -eq $Tag })
        if ($matches.Count -or $batch.Count -lt 100) { break }
    }
    if ($matches.Count -ne 1) { throw 'Expected exactly one release for this tag' }
    $remote = $matches[0]
    $names = @('update.json', $manifest.portable.name, $manifest.installer.name)
    if ($remote.assets.Count -ne 3) { throw 'Expected exactly three uploaded files' }
    foreach ($asset in $remote.assets) {
        if ($asset.name -notin $names) { throw 'Unexpected uploaded filename' }
        $local = Join-Path $Signed $asset.name
        $expectedDigest = 'sha256:' + (Get-FileHash -LiteralPath $local -Algorithm SHA256).Hash.ToLowerInvariant()
        if ($asset.state -ne 'uploaded' -or $asset.digest -ne $expectedDigest -or
            $asset.size -ne (Get-Item -LiteralPath $local).Length) {
            throw ('Uploaded file mismatch: ' + $asset.name)
        }
    }
    [ordered]@{ tag = $Tag; url = $remote.html_url; draft = $remote.draft;
        preview = $remote.prerelease; remoteHashesVerified = $true; sourcePublic = $true } |
        ConvertTo-Json | Set-Content -LiteralPath (Join-Path $Signed 'draft-verification.json') -Encoding UTF8
    Write-Host "PASS: uploaded files match. Review $($remote.html_url)"
} finally {
    $headers.Clear()
    $credentials = $null
    $credentialLine = $null
}

The additional local draft-verification.json is a report, not a release asset. Do not upload it. Never display or copy the credential variables or enable a transcript that captures manually printed secrets.

9 Publish on GitHub

  1. Open the draft URL while signed in to your GitHub account. If necessary, open AetherDesk Releases and edit the draft.
  2. Verify the version/build tag, title, notes and all three assets. Source is public in the same repository. Check that no credentials or personal test data are included.
  3. For a preview, keep This is a pre-release selected. It becomes a public manual download and is excluded from stable automatic updates.
  4. For a normal update, clear the pre-release option and select Set as latest release. Explicitly making it latest matters when increasing only the build number while keeping the same numeric version.
  5. Click Publish release only when you accept making the update available to all eligible users. There is currently no private rollout ring in AetherDesk. If it is only a draft, choose Save draft.
  6. Open the published page in a signed-out or private browser window. Check installer and portable download availability. New release tags point to the matching AetherDesk source commit; GitHub’s automatic “Source code” archives contain that source. Older build 1/2 tags predate source consolidation.

For a normal release, verify that the public latest feed returns the exact tag:

PowerShell • anonymous stable-feed check
$latest = Invoke-RestMethod 'https://api.github.com/repos/ashkanr65/AetherDesk/releases/latest'
if ($latest.tag_name -ne $Tag -or $latest.draft -or $latest.prerelease) {
    throw 'The stable update feed is not serving the intended release'
}
$latest | Select-Object tag_name,html_url,published_at

Update the public README download links to the newly published assets. Keep its validation claims accurate. A draft or preview will not pass the normal-feed check above, by design. GitHub's official release instructions describe the publication controls.

10 Test the actual update

Use an older updater-enabled AetherDesk installation. Opening the newly built version cannot prove an upgrade from the older one. Back up your old package/installer and, with AetherDesk closed, its settings folder at %APPDATA%\AetherDesk-Rust. Folder backups do not export Windows Credential Manager secrets; keep the existing Windows account and protected credentials.

Detection and download

  1. Open the older version. Select the top-right gear, then Updates and Check now.
  2. Confirm the offered release notes identify the newer build. The heading currently shows the numeric version without its build number, so two successive builds can both display “0.1.2”.
  3. Click Download update. Wait for verification and the ready-to-install state. A detection success alone does not prove download, installation or restart.

Replacement and restart

  1. Finish transfers and assistant operations, save editor changes and disconnect active tabs normally. Close other AetherDesk instances using the same installation folder. The updater blocks installation while relevant work is active.
  2. Choose Update and restart and review its confirmation. Allow the helper and application to finish; do not start a second copy, move runtime files or remove the update stage during the operation.
  3. After restart, confirm the updated installation's release.json shows the new build. Compare the EXE hash with AetherDesk.exe in the new signed inventory if stronger confirmation is needed. The About version alone may not distinguish build 1 from build 2.
  4. Verify saved sessions, settings, credentials, AI services/history and working-file recovery. Reconnect and test keyboard, mouse, file transfers, desktop sizing and the features changed in this release.
  5. Repeat with a disposable portable installation and a disposable installer installation. Success for one distribution does not certify the other. This PC alone does not establish clean-machine compatibility.

The installer path is normally %LOCALAPPDATA%\Programs\AetherDesk-Rust; portable updates replace the folder from which the old EXE was launched. Do not alter the old release.json to simulate an older build: the version and trust key are embedded into the executable.

11 Troubleshooting and recovery

What you seeWhat to do
No update offeredCheck the old EXE's real build, the normal release's latest tag, its published rather than draft state, and the pre-release option. Both version and build are compared. A preview is intentionally ignored. Do not erase version-floor settings to force a downgrade.
Signing key unavailable or mismatchedUse the original Windows account and protected key. Check the publisher Python path. Do not generate a replacement key. Recover the established key through an approved process or use the configured manual workflow.
Python or cryptography unavailableUse section 1's publisher environment. This does not require changing the application's end-user dependencies.
GitHub authorization failsConfirm write access to the AetherDesk repository using your normal Git Credential Manager account. Complete sign-in yourself. Source and releases share the public AetherDesk repository. Do not put a token in the guide or source.
Release output is not emptyUse a new timestamped signed-output folder. A failed prepare can leave a partial ZIP; never publish it.
Tag exists or an upload failedInspect the unpublished draft and its files before retrying. Never overwrite a published version/build pair. Give corrected public packages a new build number.
Source changed since the buildCheck the actual diff and package provenance. The built snapshot does not contain later changes. Rebuild when application/build inputs changed; do not bypass the provenance check to release different code.
Download or verification failsRecord the message, check connectivity, disk space and the three uploaded assets, then retry through Updates. Never edit signed metadata or disable verification.
Update and restart is unavailableFinish or save active work and close other instances from the same installation. Do not kill an active session merely to bypass the guard.
Portable update is interruptedKeep the updater's backup, journal, plan and logs. Portable replacement attempts restoration after copy or first-start failure; do not delete recovery files. If automatic recovery fails, close all instances and recover from the known-good complete portable package into a separate folder.
Installer update or first start failsKeep installer/helper logs and the previous installer. The installer uses its transaction mechanism, but automatic rollback after a failed first launch is not guaranteed. Use the retained package/installer for controlled recovery; do not delete user settings or protected credentials.
A bad normal release is already publicStop further rollout by changing its GitHub release state to a pre-release and verify what the latest normal feed serves. This does not revoke already downloaded files or roll back installed clients. Publish a corrected, higher build rather than replacing signed public assets.

12 Keep the release records

  • Retain the signed installer, flat ZIP, metadata, upload-verification report and release URL.
  • Retain the source commit, package fingerprint, build timing, native regression reports and your live-test notes before the next build clears reports.
  • Record detection, download, replacement, restart and preservation separately. Keep failed results and recovery limitations visible.
  • Update SESSION-UI-TASKS.md with completed and remaining work; commit and push documentation to main. Public release notes and README should describe only what actually passed.
  • Keep at least one working older installation/package outside the generated output folder. Do not run blanket deletion commands on source, profiles, signing material or recovery folders.

The release scripts normally need no edits between releases. Routine work is: version and notes → commit and push main → build → verify → sign → upload draft → verify remote files → publish → test the actual upgrade → record results.

This guide follows the local tools/rust-build-kit implementation and the release process used on this PC. Additional references: GitHub release management and Python virtual environments. Recheck commands if paths, scripts or the GitHub interface change. No build, publication, installation or credential operation is performed by opening this file.
